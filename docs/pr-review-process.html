The PR review process

How a pull request gets reviewed, argued with, and merged across prismalens/prismalens, prismalens/sreforge and Sumit1993/mage-memory. Living doc. Any change to a claude-*.yml workflow, a ruleset, or the resolution protocol updates this page in the same session. Last rewritten 2026-08-30, after gh-workflows#53 (per-repo config, org defaults, model escalation) and gh-workflows#37 gh-workflows enforces no ruleset, and on that repo the push is the CodeRabbit request.

1The cast

Ten parties touch a PR. The thing worth holding in your head is which of them has a model inside it, because that is the line the whole permission design is drawn along.

human model runs here deterministic automation, no model third party

Operator human

your own GitHub account

Opens PRs, rules on disputes, enqueues merges. The only party allowed to resolve a thread on judgment rather than on proof.

Local session agent

posts under the operator's credential

The Claude Code seat holding the diff. Writes the fix, pushes it, replies in each thread with the SHA.

Never resolves a claude[bot] thread and never merges without a liveness verdict.

Review lane agent

claude[bot]

Reads the diff, posts inline findings, sometimes a summary comment.

Write-capable by construction, not by invariant. It holds id-token: write, the sole input to the claude[bot] App-token mint, which carries contents: write, pull_requests: write and issues: write across the org. What keeps that power away from thread resolution and code push is the tool allowlist, not the permissions block.

Verify job agent

claude[bot], its own hardened job

Re-checks the lane's own past findings against the current head and writes one verdict per open thread.

Genuinely read-only. No id-token: write, so the App-token mint never fires, and a plain GITHUB_TOKEN capped at read. A tripwire step fails the job outright if an OIDC request environment shows up anyway.

Mention lane agent

claude[bot]

Answers a bare @claude … question on a PR. Same identity as the review lane, different workflow.

Denied gh pr review and the reviews API by explicit tool deny-list.

Mutate job deterministic

github-actions[bot]

Plain Python and gh api. Reads the verify job's verdicts, re-fetches live threads, posts one reply per thread, resolves the verified ones.

This is the only job that writes to threads, and it is the only job with no model in it. Those two facts are the same design decision. It resolves with the job's own GITHUB_TOKEN at contents: write; no GitHub App is anywhere in this lane.

Liveness job deterministic

github-actions[bot]

Upserts one comment per PR saying what the reviewer actually posted. Runs even when the review failed, which is the point of it.

CodeRabbit third party

coderabbitai[bot]

The escalation reviewer. One counter per developer, shared across every repo you touch. Automatic on gh-workflows, admitted by the coderabbit_review label everywhere else.

Fork contributor human

outside account

Gets no Claude review at all. GitHub withholds secrets from fork code and a summon does not override it. The lane says so out loud instead of going quiet.

Dependabot bot

dependabot[bot]

On the skip_authors list, so its pushes buy no automatic review. A summon still works on its PRs.

2Where the code lives

3Anatomy of one run

Six jobs, and two of them run a model. review is write-capable by construction: the wall between it and thread state is the tool allowlist, not the permissions block, because publishing a review needs a write-capable credential. verify and mutate are built to the simpler rule instead: verify holds no write at all, and the only job that writes, mutate, holds no model.

id-token: write is a passport, not a key. It does not open anything by itself; it lets a job ask GitHub for a signed statement about itself, which review then trades at api.anthropic.com/api/github/github-app-token-exchange for the claude[bot] token. Take away the permission and no passport can be issued, so no trade can happen. That is why verify omitting it, not merely under-using it, is what makes that job genuinely write-incapable rather than merely well-behaved.

Set display_report: true in a consumer stub (default false) and the review round renders its own reasoning and token/cost usage into the Actions Step Summary: a context table, a usage table (input_tokens, output_tokens, cache reads and writes, total_cost_usd, duration, turns, permission denials), and the assistant's reasoning turns as Markdown. The summary is world-readable on a public repo, the same as the diff it is derived from. A missing or unparseable execution file warns and exits cleanly rather than failing the job.

4Modes: what the review job decides to be

The review job is not one thing. Before the agent starts, a mode step reads the trigger, the PR's current thread state, and the sha= baseline from the liveness comment, and picks one of five behaviours. Almost every confusing thing about this lane comes from not knowing which mode a given run was in.

What a verify round actually is

A verify round is the lane re-checking its own past findings against the current head, instead of taking a claim that they are fixed on trust. It is the only mode whose output feeds a job that can write to threads, and the only one that can end with something resolved.

The trigger is a reply, not a push. A non-bot reply inside one of the threads is enough on its own, with no verb needed; @claude review also works. Bot identities are excluded, which is how the lane avoids retriggering on its own reply.

Per thread it reads the code at that thread's path plus the PR diff, and judges whether the concern still stands at current head. fixed resolves the thread; still_applies and cannot_verify post a templated reply citing the sha and evidence, and leave it open. The verdict is a judgement about the code, not about what the reply claimed.

What the verify job cannot do, and this is where the design lives: it holds no id-token: write, so the claude[bot] App-token mint never fires, and its own GITHUB_TOKEN is capped at read. It cannot resolve a thread, cannot post a reply, cannot post the summary comment, cannot submit a formal review, and cannot merge. It writes only the schema-validated verdicts; mutate does every post, from its own templates. A permanent tripwire step fails the job outright if an OIDC request environment shows up anyway, so the mint path stays dead even if the permission ever leaks back in through a workflow edit or a drifted tag.
The consequence people trip on. Push a fix and nothing gets verified: a push lands on incremental or review, never verify. The thread stays open, the merge stays blocked, and the liveness comment cheerfully reports a successful review. You have to reply in the thread. That single fact explains most "why is this still blocked" confusion, and it is deliberate: a push is a claim about code, a reply is a claim about a specific finding, and only the second one tells the lane which threads to re-check.

5The token question

Resolving a review thread needs contents: write. Nothing else about the credential matters. Posting a reply needs only pull-requests: write, which is why the original failure was so confusing: the same token in the same step posted the reply and was refused the resolution.

Resolving a thread therefore costs a credential that can also push code. That is the reason the mutate job contains no agent: the grant is real, so nothing model-influenced may ever hold it. That part of the design is right and should not move.

Which credential, and why the App is gone

Settled: GITHUB_TOKEN carries mutate, at contents: write. No GitHub App, no installation, no per-repo secret mapping. The canary above ran on prismalens/prismalens, a repo that never held App credentials in the first place, which is the strongest version of the proof: nothing repo-specific was required for a thread to resolve.

The App existed to separate the writer of a fix from its judge, and that reason did not survive scrutiny: two credentials with identical permissions separate nothing. Dropping it also dropped the entire config surface that had already broken one of the three repos: nothing left to install per account, nothing to map by secret name per consumer, nothing to drift. Six secrets and the App installation were deleted 2026-08-29. Story: gh-workflows#20, #37.

6Configuration: four layers, one key at a time

Review settings resolve dynamically, evaluated lowest to highest precedence, and the merge is per key, not per file: a repository may set only default_model and still inherit auto_pause_rounds, skip_authors and path_filters from whichever layer below it last set them.

Three outcomes at layers 2 and 3: absent (HTTP 404) applies the layers below with a plain info line and no warning; malformed YAML, unknown keys, or a disallowed value emits a ::warning:: naming the file, the ref, and the validator's error, then ignores that layer entirely; valid consumes the wired keys and logs a warning for any schema-valid but unwired key. Wired: review.default_model, review.auto_pause_rounds, review.skip_authors, review.path_filters. Schema-accepted but not yet wired, warned if present: review.path_instructions, findings.suppress_below, findings.enable_ai_fix_prompt, findings.include_verification_note.

Model escalation from changed files

The model is chosen once, up front, before the agent runs. Default is review.default_model. If review.path_filters is set, by either config layer, and a changed file in the PR matches one of its glob patterns (fnmatch, with a trailing /** matching a directory and everything under it), the model escalates to Opus. An explicit --model <alias> in a summon always wins over path escalation. Which model ID an alias actually resolves to is decided by the CLAUDE_CODE_OAUTH_TOKEN subscription, not by this input.

The liveness comment names both the model and model_source, the reason it was picked: default, summon override, escalated by path match, or default (changed-files fetch failed). An unrecognized --model alias falls back to default_model and emits a warning rather than failing silently. Neither of the three consumer repos has added a .github/claude-review.yml yet, so today all three run on org and workflow defaults alone.

7Scenarios

Same five parties every time. What changes is who speaks and who stays quiet.

7.1 The normal round: finding, fix, verify, resolve

The verify agent does not take your word for it. A reply of Fixed in 7eed363 on a finding that is not actually fixed draws back "Still applies to 7eed363d: scripts/canary-retention.sh line 11 still uses unquoted $ARTIFACT_DIR in the find -delete call; the seeded bug is unchanged at current PR head." The thread stays open. This is the single most important property of the whole design, because it is what makes automatic resolution something other than a rubber stamp.

7.2 A finding you disagree with

7.3 A caller stub still capped at contents: read

mutate cannot grant itself more than the caller declares: a job's permissions: block is capped by the ceiling the consumer's stub sets on the whole call. All three live consumers already declare contents: write, so this is a fresh-consumer risk, not a live bug, but the shape is worth knowing because it used to be the exact failure mode the now-deleted App was defended on.

There is no silent-degradation state left. The old design's worst failure was a green job with a thread reading "Verified fixed" that still blocked the merge, because a missing App credential degraded to a warning nobody read. A denied mutation now exits the job non-zero instead of printing an error and carrying on, so the one gap that mattered is closed by construction rather than by remembering to wire a secret correctly.

7.4 The four silences

The lane going quiet is normal and means four different things. None of them mean approval. Every one of them puts a sentence on the PR saying which it was, which is the whole reason the announce job runs on always().

7.5 A fork PR

7.6 Spending a CodeRabbit review

CodeRabbit is the independent second opinion, spent on changes where being wrong is expensive and where a reviewer sharing no model, prompt or failure mode is worth having. The counter is per developer, not per repo: all three repos draw one pool, and a review costs roughly a 40-minute cooldown across all of them.

Once a PR is admitted, auto_pause_after_reviewed_commits: 1 stops a fix-push loop from spending the counter again on every push. Batch the fixes, push, reply with SHAs, then re-request explicitly. Never write the word "resolve" in a reply to CodeRabbit: it parses as a command and no-ops the reply.

gh-workflows is the exception and reviews automatically, because it is the one repo the Claude lane refuses to review. Everywhere else, "Review skipped: excluded by label configuration" is the valve working.

On gh-workflows the push is the request. There is no separate summon step to hold back, so "don't trigger CodeRabbit, I'll do it once this lands" is an instruction a lane cannot obey by pushing: the first push spends the slot on its own. Batch before you push there, not before you summon. Later pushes are covered by auto_pause_after_reviewed_commits: 1 and surface as CODERABBIT AUTO-PAUSED rather than spending again. Batching-before-summon is advice for the label-gated repos only.

gh-workflows enforces nothing at merge. gh api repos/prismalens/gh-workflows/rulesets returns []: no required check, no thread-resolution gate. The other three repos each carry one active ruleset with CI gate, Validate PR title (conventional commits) and required_review_thread_resolution. Holding the PR until the review has been read is the only gate the canon repo has. Read enforcement off rulesets; all four repos 404 on branches/<b>/protection because none of them use classic branch protection, so that 404 distinguishes nothing.

8Who resolves this thread

9Reading the liveness comment

Every PR gets exactly one, from github-actions[bot], updated in place. Match the marker prefix, never the whole string: the field set changes, and an exact-string matcher silently stops finding the comment.

It is not a display. It is where the lane keeps its state. rounds= is read back by the mode step on every automatic round and is what enforces auto-pause. sha= is the reviewed-head baseline that incremental review is designed to consume. Deleting the comment deletes auto-pause and the incremental baseline with it, so it cannot go anywhere until something else holds that state. Its display half also still earns its place: "a green job is never evidence" is the invariant this lane was built around, and this comment is the only thing that answers it on the PR itself. It also names the model and why that model was picked (default, summon override, or escalated by path match), and on an incremental round it names the range: "reviewed `<head>` (incremental from `<base>`)".

10Summoning

Bare PR comments from an OWNER, MEMBER or COLLABORATOR. The comment body is read only by workflow contains() expressions and never reaches a prompt or a shell string. That rigidity is the security property, not an oversight, which is why the model override is an allowlist of two fixed phrases rather than a parsed argument.

What you typeWhat happens
@claude reviewA verify round wins when unresolved claude[bot] threads exist. Otherwise the round is scoped to the commits since the last reviewed sha=: incremental on a clean compare range, a full review on any of the six fallback reasons. On a head already reviewed with no open threads it gives a full review rather than doing nothing. The resume for an auto-paused PR, resetting rounds=0 when it posts output.
@claude review --model opus
@claude review --model sonnet		Same, on the model ID mapped to that alias in model_aliases (default opus=claude-opus-5,sonnet=claude-sonnet-5). The alias is matched independently of the verb, so it composes with full review too. An unrecognized alias falls back to default_model and emits a warning rather than failing silently.

a plain reply inside a threadNo verb needed. A non-bot in-thread reply is itself the verify trigger.

Summons run on drafts, bypass skip_authors, and reset the auto-pause counter to 0 whenever they post review output, not merely bypass it for one round. They do not override the fork guard or the self-skip. @claude full review --model opus now resolves the model correctly: the alias match no longer shares a string with the verb match, so the two compose instead of one silently swallowing the other.

11Standing rules

  • A green job is never evidence a review happened. The action exits success having posted nothing. Only published output counts, and the liveness comment is where you read it.
  • Automatic review is finite, and a summon is the only resume. Anything waiting on a machine review reads the verdict rather than the absence of one.
  • The wall around write power is the tool allowlist, not the permissions block. review holds id-token: write and is write-capable by construction; what keeps it from resolving threads or pushing code is which tools it may call. verify is the one job with no write access at all, by permissions. The mention lane holds none either. If a change widens either allowlist toward gh pr review, gh api, or a resolve call, the change is wrong.
  • The mutate job never holds a model. It holds a credential that can push code, which is the same statement from the other side.
  • Verdicts are data, not instructions. The mutate job re-fetches live threads and matches them itself. Nothing the agent wrote is executed.
  • Canary before trust. After any lane change lands: open a trivial docs PR, let the round run, read the liveness comment, close it unmerged. gh-workflows#18 exists because a canary was run and the feature did not work.
  • Lane logic changes happen in prismalens/gh-workflows only. Consumers hold thin stubs.
