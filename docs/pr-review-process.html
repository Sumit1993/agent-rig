Reviewers left 3 comments. One @claude fix or three?

One. One summon comment per round — this is the @claude fix trigger, not a reply protocol; fix replies always go in-thread: @claude fix. The fixer's prompt tells it to read all unresolved review threads on the PR and address each — replying in every thread it touched with the fix commit SHA. Commenting per-thread would start one full agent run per comment (they serialize per-PR, but each spends subscription for nothing). Add scoping words only to exclude: e.g. @claude fix — only the two SCHEMA.md threads, leave the API design one for me.

Never let the fixer resolve anything — it is denied the tools, and the deny list is load-bearing: threads are the only thing standing between a pushed "fix" and a merge. The fixer fixes and replies; verification belongs to a different party. Disputes: operator tie-breaks.

Reading the liveness comment

Every PR gets one auto-updated comment from github-actions[bot]: "reviewed abc12345 and posted N inline / M summary comment(s)" means the reviewer ran and published. "posted nothing" means this head has no machine review on record — silence is never approval. A PR that edits claude-code-review.yml itself is never reviewed by the lane (self-skip is a security control): label it coderabbit_review for a CodeRabbit read instead.

When to spend a CodeRabbit review

Apply the coderabbit_review label (or comment a bare @coderabbitai review). A PR without the label shows "Review skipped: excluded by label configuration" — that is the valve working, not an error. It's an org-wide, ~40-min-cooldown counter — spend it on security-sensitive paths, workflow changes, or a second opinion; never routinely. Batch your fixes before re-requesting.

Merging

  • prismalens, sreforge: gh pr merge N --squash enqueues; the queue tests a speculative merge onto main and lands it. No more update-branch / BEHIND cascades, no full-CI reruns per sibling merge.
  • mage-memory: classic squash (merge queue is org-only). Update-branch still applies there.
  • Bots never merge, anywhere. The fixer is tool-denied both gh pr merge and the REST merge endpoint.

4Standing doctrine

  • A green job is never evidence a review happened. The action exits success when the reviewer posts nothing. Only posted output counts: inline threads, a ## Code review summary, the liveness count.
  • Canary before trust. After any lane lands on a new repo or a workflow change merges: open a trivial docs PR, wait for the review run, read the liveness comment. Close the canary unmerged.
  • Consumers hold thin caller stubs; lane logic changes happen in prismalens/gh-workflows only. Reusable workflows live in canon (prismalens/gh-workflows); consumers hold thin caller stubs. Lane logic changes happen in prismalens/gh-workflows only.
  • CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1 stays on every lane until upstream print mode survives background-subagent gaps (async launches end one-shot sessions before results arrive — the bug that silenced reviews for two days). Unpin = remove the env var, then re-canary; a green run is not verification.
  • Reviewer lanes are read-only; the fixer holds the only model-adjacent write, fork-guarded (resolve-pr job) and tool-denied from reviewing/resolving/merging. Don't add writes to any other lane.
