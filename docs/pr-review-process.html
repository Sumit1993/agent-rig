The PR review process

How a pull request gets reviewed, argued with, and merged across prismalens/prismalens, prismalens/sreforge and Sumit1993/mage-memory. Living doc. Any change to a claude-*.yml workflow, a ruleset, or the resolution protocol updates this page in the same session. Last rewritten 2026-08-27, after gh-workflows#19 ("give the mutate job a token that can actually resolve threads").

1The cast

Nine parties touch a PR. The thing worth holding in your head is which of them has a model inside it, because that is the line the whole permission design is drawn along.

human model runs here deterministic automation, no model third party

Operator human

your own GitHub account

Opens PRs, rules on disputes, enqueues merges. The only party allowed to resolve a thread on judgment rather than on proof.

Local session agent

posts under the operator's credential

The Claude Code seat holding the diff. Writes the fix, pushes it, replies in each thread with the SHA.

Never resolves a claude[bot] thread and never merges without a liveness verdict.

Review lane agent

claude[bot]

Reads the diff, posts inline findings, and on a verify round writes a per-thread verdict file.

Holds no write permission at all. It cannot comment through the API, resolve anything, or reach GraphQL. Its allowlist has no gh api entry.

Mention lane agent

claude[bot]

Answers a bare @claude … question on a PR. Same identity as the review lane, different workflow.

Denied gh pr review and the reviews API by explicit tool deny-list.

Mutate job deterministic

prismalens-automation[bot], or github-actions[bot] without the App

Plain Python and gh api. Reads the verdict file, re-fetches live threads, posts one reply per thread, resolves the verified ones.

This is the only job that writes to threads, and it is the only job with no model in it. Those two facts are the same design decision.

Liveness job deterministic

github-actions[bot]

Upserts one comment per PR saying what the reviewer actually posted. Runs even when the review failed, which is the point of it.

CodeRabbit third party

coderabbitai[bot]

The escalation reviewer. One org-wide counter, roughly one review per 40 minutes. Automatic on gh-workflows, admitted by the coderabbit_review label everywhere else.

Fork contributor human

outside account

Gets no Claude review at all. GitHub withholds secrets from fork code and a summon does not override it. The lane says so out loud instead of going quiet.

Dependabot bot

dependabot[bot]

On the skip_authors list, so its pushes buy no automatic review. A summon still works on its PRs.

2Where the code lives

3Anatomy of one run

Five jobs. The one with the model in it holds no write permission, and the ones that write hold no model. Everything else in this document follows from that split.

4Modes: what the review job decides to be

The review job is not one thing. Before the agent starts, a mode step reads the trigger and the PR's current thread state and picks one of four behaviours. Almost every confusing thing about this lane comes from not knowing which mode a given run was in.

ModeFires whenThe agent doesRuns after
skipNo OAuth token reached the lane, or the PR hit the auto-pause limit.Nothing. It never starts.announce only, saying which of the two it was.
reviewAny push. Or a comment trigger when no unresolved claude[bot] threads exist.Reviews the diff, posts inline findings, sometimes a summary.announce. mutate does not run.
review-full@claude full review, always, regardless of thread state.Same, from scratch, with dedup explicitly disabled so a re-review can publish findings it published before.announce. mutate does not run.
verifyA comment trigger, not full review, and at least one unresolved claude[bot] thread exists.Three things, below.announce and mutate, which is what makes resolution possible.

What a verify round actually is

A verify round is the lane re-checking its own past findings against the current head, instead of taking a claim that they are fixed on trust. It is the only mode whose output feeds a job that can write to threads, and the only one that can end with something resolved.

The trigger is a reply, not a push. A non-bot reply inside one of the threads is enough on its own, with no verb needed; @claude review also works. Bot identities are excluded, which is how the lane avoids retriggering on its own reply.

Per thread it reads the code at that thread's path plus the PR diff, and judges whether the concern still stands at current head. verified means fixed; not_verified means the finding survives. The verdict is a judgement about the code, not about what the reply claimed.

What a verify round is forbidden to do, and this is where the design lives: it cannot resolve a thread, cannot post a reply inside a thread, cannot submit a formal review, and cannot merge. It writes a file and posts comments. Everything that touches thread state happens afterwards, in a job with no model in it. The prompt even forbids writing the word "resolve" as an instruction in any comment, because CodeRabbit parses that word as a command.
The consequence people trip on. Push a fix and nothing gets verified, because pushes produce review rounds. The thread stays open, the merge stays blocked, and the liveness comment cheerfully reports a successful review. You have to reply in the thread. That single fact explains most "why is this still blocked" confusion, and it is deliberate: a push is a claim about code, a reply is a claim about a specific finding, and only the second one tells the lane which threads to re-check.

5The token question

Resolving a review thread needs contents: write. Nothing else about the credential matters. Posting a reply needs only pull-requests: write, which is why the original failure was so confusing: the same token in the same step posted the reply and was refused the resolution.

Resolving a thread therefore costs a credential that can also push code. That is the reason the mutate job contains no agent: the grant is real, so nothing model-influenced may ever hold it. That part of the design is right and should not move.

Which credential, then

This is a live decision, not settled doctrine. The App is what shipped; GITHUB_TOKEN now demonstrably works too.

GITHUB_TOKEN at contents: writeApp installation token
Config surfaceNone. Nothing to forward, nothing to install, nothing to drift.Two secrets per repo, one App install per account, one stub mapping per consumer. One of three repos is currently mis-wired.
Blast radius if leakedOne job, one repo, expires with the run.A shared private key covering every repo the App is installed on.
Workflow-wide ceilingThe caller must raise its ceiling to contents: write, which covers every job in the callee. review still self-restricts to read, but the ceiling stops being a second line of defence.Ceiling stays contents: read. The read-only invariant on review is enforced twice.
Identity on the threadgithub-actions[bot], same as the liveness comment.prismalens-automation[bot], so the audit trail names which automation closed it.
Isolation from the review agentIdentical. Job-level permissions: scopes each job's token independently, so neither option gives review anything it does not declare for itself.
My read. The ceiling is the only argument that survives scrutiny, and it is weaker than it looks: it defends against a future edit to review's own permissions block, which would be a visible change to the one file CodeRabbit reviews automatically. Against that, the App's config surface has already produced a real, currently-broken repo. A test in tests.yml asserting review's permission block byte for byte is a stronger guarantee than a ceiling, because it fails on the pull request that breaks it and it also catches the case a ceiling cannot: someone raising both at once. I would drop the App, hold contents: write in mutate only, and buy the invariant back with that test. The counter-argument I would actually listen to is the identity one, and it is worth deciding on its own terms rather than as a side effect.

6Scenarios

Same five parties every time. What changes is who speaks and who stays quiet.

6.1 The normal round: finding, fix, verify, resolve

The verify agent does not take your word for it. A reply of Fixed in 7eed363 on a finding that is not actually fixed draws back "Still applies to 7eed363d: scripts/canary-retention.sh line 11 still uses unquoted $ARTIFACT_DIR in the find -delete call; the seeded bug is unchanged at current PR head." The thread stays open. This is the single most important property of the whole design, because it is what makes automatic resolution something other than a rubber stamp.

6.3 No resolver credential: the failure that looks like success

This is the live state on prismalens/prismalens right now. Both secrets are set on the repo. The caller stub never passes them, and a reusable workflow can only see what its caller explicitly maps: secrets in a workflow_call callee contains the mapped names and nothing else, so a secret existing on the repo is not the same as the lane being able to read it. sreforge and mage-memory got the stub change; this repo did not. This whole failure class exists only because the App needs wiring, which is the strongest practical argument in section 5.

The third state fails loudly, by design. If the credential is present and the mutation is denied, the job exits non-zero rather than printing an error and carrying on. The gap is the middle column above: credential simply absent degrades to a warning on a green job, and a two-line fix to prismalens/prismalens's caller stub closes it.

6.4 The four silences

The lane going quiet is normal and means four different things. None of them mean approval. Every one of them puts a sentence on the PR saying which it was, which is the whole reason the announce job runs on always().

6.5 A fork PR

6.6 Spending a CodeRabbit review

CodeRabbit is the independent second opinion, spent on changes where being wrong is expensive and where a reviewer sharing no model, prompt or failure mode is worth having. The counter is per developer, not per repo: all three repos draw one pool, and a review costs roughly a 40-minute cooldown across all of them.

Once a PR is admitted, auto_pause_after_reviewed_commits: 1 stops a fix-push loop from spending the counter again on every push. Batch the fixes, push, reply with SHAs, then re-request explicitly. Never write the word "resolve" in a reply to CodeRabbit: it parses as a command and no-ops the reply.

gh-workflows is the exception and reviews automatically, because it is the one repo the Claude lane refuses to review. Everywhere else, "Review skipped: excluded by label configuration" is the valve working.

8Reading the liveness comment

Every PR gets exactly one, from github-actions[bot], updated in place. Match the marker prefix, never the whole string: the field set changes, and an exact-string matcher silently stops finding the comment.

It is not a display. It is where the lane keeps its state. rounds= is read back by the mode step on every automatic round and is what enforces auto-pause. sha= is the reviewed-head baseline that incremental review is designed to consume. Deleting the comment deletes auto-pause and the incremental baseline with it, so it cannot go anywhere until something else holds that state. Its display half also still earns its place: "a green job is never evidence" is the invariant this lane was built around, and this comment is the only thing that answers it on the PR itself.

9Summoning

Bare PR comments from an OWNER, MEMBER or COLLABORATOR. The comment body is read only by workflow contains() expressions and never reaches a prompt or a shell string. That rigidity is the security property, not an oversight, which is why the model override is an allowlist of two fixed phrases rather than a parsed argument.

What you typeWhat happens
@claude reviewIncremental. The lane picks its own mode: a verify round if unresolved claude[bot] threads exist, otherwise a normal review. The only resume for an auto-paused PR, and it buys exactly one run.
@claude review --model opus
@claude review --model sonnet		Same, on a pinned model ID. Default is claude-sonnet-5, deliberately: the review lane is the highest-volume Claude spend across the three repos.
@claude full reviewFrom scratch with dedup disabled. Existing comments are explicitly not dedup targets, without which a re-review publishes nothing. This is the right answer to a "posted nothing" verdict.
a plain reply inside a threadNo verb needed. A non-bot in-thread reply is itself the verify trigger.
bare @claude …Routes to the mention lane, which answers questions and holds no write permission.

Summons run on drafts, bypass skip_authors, and ignore the pause counter. They do not override the fork guard or the self-skip. Known gap: @claude full review --model opus silently uses the default model, because the literal @claude review --model opus is not a substring of it.

10Standing rules

  • A green job is never evidence a review happened. The action exits success having posted nothing. Only published output counts, and the liveness comment is where you read it.
  • Automatic review is finite, and a summon is the only resume. Anything waiting on a machine review reads the verdict rather than the absence of one.
  • The reviewing job never holds a write. Not the review lane, not the mention lane. If a change wants to add one, the change is wrong.
  • The mutate job never holds a model. It holds a credential that can push code, which is the same statement from the other side.
  • Verdicts are data, not instructions. The mutate job re-fetches live threads and matches them itself. Nothing the agent wrote is executed.
  • Canary before trust. After any lane change lands: open a trivial docs PR, let the round run, read the liveness comment, close it unmerged. gh-workflows#18 exists because a canary was run and the feature did not work.
  • Lane logic changes happen in prismalens/gh-workflows only. Consumers hold thin stubs.
