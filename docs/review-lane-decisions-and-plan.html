Review lane: decisions and plan

What Fable ruled on the resolution grant, what the telemetry research found, what the secrets audit found, and the order the work has to land in. 2026-08-27. Nothing here has been implemented; every repo is untouched.

1What was decided

upheld

1 · The authorization survives

The invariant the earlier ruling protected was "no model holds write over code or merge state", not the name of a permission scope. The shipped review/mutate split honours it better than the design that was actually ruled, which put the resolving credential inside the agent's own job.

Changes: the split becomes the design of record. The old "give the reviewer pull-requests: write" instruction is void.

upheld, scoped

2 · The allowlist wall stands, for review only

Treat the review job as write-capable behind a tool allowlist, because it must be presumed to be. Tolerable where nothing downstream automates on the output. Not tolerable for the verify round, whose output drives a job with push access.

Changes: nothing on the review round. The verify round is fixed structurally by ruling 4.

reversed

3 · GITHUB_TOKEN carries mutate

Delete the App-token path entirely. prismalens-automation was created 58 minutes after the fixer lane was deleted, for one reason: GITHUB_TOKEN appeared unable to resolve threads. That premise is measured false. The only other candidate reason, separating the writer of a fix from its judge, died with the fixer, and an earlier ruling had already disposed of it: "two apps with identical permissions separate nothing".

Changes: ceilings rise to contents: write, both jobs keep explicit permission blocks, six secrets and one App installation get deleted.

new work

4 · Split the runtimes

Fable ruled the verify round off the agent harness onto the Messages API. That route is rejected on billing, and the ruling's property is reached instead by hardening the round in place and splitting it into its own job. Amendment accepted; ruling 4 closes as satisfied by other means. See P3.

Changes: the verify round becomes a separate job holding a read-only GITHUB_TOKEN, no id-token, and no way to mint anything.

no change

5 · Merge gate untouched

Document the consequence: with resolution automated and 0 required approvals, a wrong close becomes an unattended merge. The guard that exists, resolving comments citing commit and evidence, is the right one.

Changes: a written revisit trigger. On the first observed wrong close, set required_approving_review_count: 1 on that repo. Not a lane redesign.

2Credentials, in plain English

Four different credentials show up in this lane and they get confused constantly, including by me earlier in this document. They are not variations on one thing. They come from different places, they can touch different things, and only some of them are yours to control.

The three that touch GitHub

The fourth is CLAUDE_CODE_OAUTH_TOKEN, and it is not a GitHub credential at all. It is your Anthropic subscription login, so the action can talk to Claude. It cannot touch your repository. It stays exactly as it is.

What an id-token is, and why it is not a key

This is the one that confused me and cost this document a correction. id-token: write does not give the job a token that opens anything. It gives the job the right to ask GitHub for a signed statement about itself: "this is a run of workflow X, in repository Y, on branch Z, and GitHub vouches for that."

Think of it as a passport rather than a key. It proves who you are. It opens nothing. Its value is that somebody else trusts the country that issued it, and will hand you one of their keys in exchange.

Downscoping at mint time

A GitHub App is installed once, with a set of permissions. That set is a ceiling, not the grant. Every time a job turns the App's private key into a usable token, it says how much of that ceiling it wants, and it can ask for less.

So what is actually happening to the secrets

Three separate things are going on, and lumping them together is most of the confusion.

And one rule that explains all the mapping boilerplate. A reusable workflow can only see secrets its caller hands it by name. secrets: inherit looks like a shortcut and does not cross an ownership boundary, so a personal-account repo calling an org workflow silently gets nothing. That is why every caller stub lists each secret explicitly, and it is exactly how prismalens/prismalens ended up holding two secrets the lane could not read.

The verdict schema that makes it work

Three states rather than two. That is what lets the "still applies to <sha>" reply move out of the agent and into mutate.

VerdictWhat mutate does
fixedRe-derive, validate sha and ancestry, resolve, post the templated reply.
still_appliesPost the open-thread reply from a template it owns, citing sha and evidence. Leave open.
cannot_verifySame as above, different template. Leave open.
The schema arrives without leaving the action. claude-code-action has a structured_output step output, populated when --json-schema is passed in claude_args. That kills the write-JSON-to-a-path contract, and with it the only reason Write is in the verify allowlist.

5Telemetry: what is actually possible

Anthropic exposes no programmatic usage data for subscription plans. The Admin endpoints (/v1/organizations/usage_report/*, /v1/organizations/cost_report) cover metered API-key organisations only. On claude.ai you get the 5-hour and 7-day utilisation bars and nothing else.

So every workable option captures token counts client-side on the runner and multiplies by public pricing. Those are API-equivalent estimates, not what a subscription is billed. They are still the right relative measure for "which round type is eating the budget", which is the question worth answering.

Tagging is the part that answers your question. Both routes attach github.repository, the PR number and the round type: route A as fields on the row you POST, route B through OTEL_RESOURCE_ATTRIBUTES. That is what turns raw token counts into "the verify round on sreforge costs this much".

Where openusage fits, corrected

An earlier draft of this page wrote openusage off for CI. That was wrong, and only one third of it holds up. The docs draw a sharper line than I did.

PieceFitWhat the docs actually say
openusage hubnot for CI "Snapshot is the latest, not a stream. The hub holds only the newest batch per machine. If you want historical aggregates, query each daemon's SQLite separately." Plus entries are pruned after hub.stale_timeout_seconds, default 300s. Ephemeral runners are exactly the case this cannot hold.
openusage session --json
daily / blocks / weekly		 built for this "Headless usage and cost reports printed to stdout as an aligned table or, with --json, as machine-readable JSON. They reuse the same local parsing and pricing as the dashboard, so you can script spend tracking in CI without running the TUI." The docs name the use case outright.
5-hour blocks and the utilisation gaugethe signal that actually binds blocks groups usage into 5-hour billing windows, showing burn rate in $/hour and a projected end-of-block cost. The provider page also reads GET https://api.anthropic.com/api/oauth/usage with the Claude Code OAuth token for the 5h and 7d utilisation gauges.
The correction that matters most. On a subscription, dollars are a proxy and the 5-hour rolling window is the thing that actually stops you working. execution_file gives you total_cost_usd, an API-equivalent estimate of money you are not billed. openusage models the block and the utilisation gauge, which is the subscription-native signal. Those answer different questions, and the second one is closer to the one you asked. Track both.

Which extractor, and the one measurement that decides

Two candidates for the runner, and they read different sources:

  • execution_file. Always written by the action, one file per run, carries per-turn token breakdown and an SDK-computed total_cost_usd. No binary to install. Guaranteed present.
  • openusage session --json. Reads ~/.claude/projects/**/*.jsonl, so it needs the CLI to have written transcripts to the standard location. Costs a binary install per job, and gives you a maintained pricing table plus session and block structure for free rather than hand-rolled.
Open question, one CI run settles it. The action drives Claude through the SDK (run-claude-sdk.ts), and it is not established whether a print-mode SDK session leaves transcripts under ~/.claude/projects/ on the runner at all. If it does, openusage is the better extractor and you inherit its pricing and block logic. If it does not, execution_file is the only source and openusage stays a laptop tool. Add ls -R ~/.claude/projects/ || true as a debug step on one review round and the answer arrives free.

Two options that do not work at all, so nobody re-derives them: LLM proxies (LiteLLM, Portkey, Helicone) cannot see subscription OAuth traffic, and the Anthropic Admin usage API covers API-key billing only.

7The plan

P0 · Telemetry. Start here.

Additive, touches nothing security-relevant, and a week of its data tells you whether P3 is worth building. Repo: prismalens/gh-workflows.

  1. Add a post-step to the review job reading ${{ steps.claude-review.outputs.execution_file }} and the verify round's equivalent. Sum tokens by type, take total_cost_usd from the final result entry.
  2. Tag each row: repository, PR number, head sha, round type (review / review-full / verify), model, run id, session_id.
  3. Write it to $GITHUB_STEP_SUMMARY so it is visible on the run without leaving GitHub.
  4. POST the same row to an Apps Script Web App backed by a Sheet. One new secret, USAGE_SINK_URL, mapped in the three caller stubs. Failure to POST must never fail the job.
  5. Step 0, actually. Add ls -R ~/.claude/projects/ || true to one review round first. If transcripts are there, use openusage session --json as the extractor instead of a hand-rolled parser and inherit its pricing table and 5-hour block logic.
  6. Separately, install openusage on the laptop and watch openusage blocks. On a subscription the 5-hour window is what actually binds, and no amount of dollar-estimate tracking in CI tells you how close you are to it.
  7. Let it run a week before touching P3.

Open question to settle while building: whether the post-step runs when the review step failed or was cancelled, since those runs still consumed budget and are the ones most worth seeing.

P3 · Split the verify round into its own hardened job. After P0 has data.

The runtime stays Claude Code. Per-token API spend for a recurring round is not wanted, so the Messages API route is off. Fable's amendment accepts that and closes ruling 4 as satisfied by other means, on one structural condition it added.

The condition: verify must become its own job. The two changes that matter are job-scoped, and the verify step currently shares the review job's permissions block, which has to keep id-token: write for the review round. Done at step level, the App-token mint path still sits in the same job as the verify agent, held back by nothing but the allowlist. That is exactly the shape ruling 4 refused. Split out, the verify job holds a read-only GITHUB_TOKEN, no id-token, and no OIDC request environment, so nothing in it can mint anything regardless of later allowlist edits.
Correction to what this page said before. I had id-token: write down as serving only Workload Identity Federation, reading action.yml:74. It has a second use I missed, and Fable found it in src/github/token.ts: it is the sole input to the claude[bot] App-token mint, via core.getIDToken() exchanged at api.anthropic.com/api/github/github-app-token-exchange, which requests contents: write, pull_requests: write and issues: write by default. The correction strengthens the change rather than undermining it: dropping the permission removes the mint path fail-closed, instead of merely tidying an unused declaration.

What moves, and what does not

  • The summary comment and the open-thread replies move to mutate, which already posts and owns templates. The three-state verdict schema is unchanged.
  • The "Verify summary comment was posted" guard is deleted, not moved. It exists because an agent can silently skip a step. A templated post from deterministic mutate cannot skip itself, so the guard has nothing left to catch.
  • The delta review is dropped, not rehomed. Three reasons, and the third is the one nobody had spotted: it cannot post under the hardened job; routing model-authored finding prose through mutate would make the write job render free text and break its bounded-fields design; and it is a bypass of the auto-pause gate, because verify triggers on comment events that never read the rounds counter. Residual coverage for paused, cancelled and draft heads is already the liveness comment plus @claude review.

The #12 collision, ruled

Confirmed with one edit. Keep increment 2's range-limiting substance; delete the clause saying verify is deleted and its verdict duty absorbed into the vendored prompt. Mode set becomes skip / review / incremental / verify. Absorption would put the verdict channel back inside the claude[bot]-credentialed job, and with the delta review gone the two rounds no longer overlap, so it has no remaining purpose.

New rule to encode now, before increment 2 is built. announce must never advance the sha= baseline on a verify round. Without it, increment 2's commit range would start past commits no review round ever read, and swallow them permanently. This is the same class of bug the baseline was created to prevent.

Canaries

One seeded run on a scratch PR settles the lot: log lines proving no OIDC exchange happened and the revoke step was skipped; structured_output populated and passing the gate, which also settles whether --json-schema takes a file or an inline form; gh pr diff and the actor permission check working under the job token; and the mutate and announce plumbing. If --json-schema fails in both forms, the verify round stays loudly broken rather than falling back to Write.

What is accepted as lost. Server-side constrained decoding becomes client-side CLI validation, hence change 6. "Structurally impossible to widen" becomes "widening reaches only more reading", which is acceptable because the credential genuinely cannot write, provided the README names the two load-bearing lines, no id-token on the verify job and github_token passed, so reintroducing either reads as an invariant change rather than a tidy-up. The harness reliability tax stays. That is the price of the billing decision, paid knowingly.
